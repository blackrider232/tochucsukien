## What is built

- **Sending model.** Gmail is called from the browser with a Google Identity Services token kept in memory (design.md, open question on Gmail). The token belongs to the Google account the officer signs in to on the compose card, not the app account, and the card says so. A unit mailbox can be the From only when it is the account signed in (m4a B29). There is no sandbox (decision 16). "Gửi thử cho tôi" really sends one message to the officer signed in to the app.
- **Campaigns and the no-double-send rule.** A campaign is one message: its id is derived on the server from the event and the subject and body templates, which `comms.startCampaign` keeps with the QR choice in `sce_tcsk_email_campaigns`, so "Gửi lại thư lỗi" reopens exactly that message. A stored campaign whose subject and body do not give its id is refused before anything is claimed. Every press of a send button is one run with a random token. Before it sends, the run claims every address with `comms.startCampaign`: the row becomes `queued` under its token. A row keeps only `claimHash` of the token (sha256, as a uuid), so reading it does not reveal the token. An address that already received the message is refused. One that another run holds is left alone: `inFlight` for another officer, `ownInFlight` for another tab or the page before a reload of the same officer. Only the explicit "Tiếp quản phiên gửi" (behind a warning) takes the officer's own claims over. A claim untouched for 30 minutes plus a 2-minute clock-skew margin is a dead run's and any run may take it. A claim call that fails part-way deletes the claims it made before it fails, since the browser never learns of them. Just before it hands a message to Gmail, the run's claim of that address is `sending`: `comms.markSending` marks the run's first message, and each `comms.recordDeliveries` marks the run's next message (`next`) in the same write. The mark answers `held`; a claim the run lost stops it as `claim_lost`, and a mark whose answer was lost stops it as `not_marked`, both unsent. A `sending` row is never claimed again: once its lease runs out, or when its officer takes the run over, the next claim turns it `unknown`. A live run calls `comms.renewClaims` before a message once 5 minutes have passed; it renews every row the run holds, the `sending` one of a rate-limit retry included, and the run stops as `claim_stale` once its last good renewal is 20 minutes old. `comms.recordDeliveries` completes only rows this run holds (`queued` or `sending`): `sent` with Gmail's message id (a DB check), `error` with Gmail's reason, `unknown` when Gmail's answer was lost; the run may still record `sent` on its own row after it turned `unknown`, the same result twice is not an error, and a later result never erases a success. The browser retries a record that fails. `comms.releaseDeliveries` frees only the run's own claims it never handed to Gmail; a `sending` one goes back to `queued`, with the token, before it is deleted. The browser loop is the pure `runCampaign` (`domain/campaign.ts`) over `dispatch` (spacing 1.2 s, retry with backoff on 429/5xx, stop on 401, daily quota, a lost answer, and when a result cannot be recorded after retries).
- **The rules in the database.** `202611041460_comms_delivery_guard.sql`, `202611041480_comms_delivery_delete_guard.sql` and `202611041490_comms_guards_no_restoring_setting.sql` enforce them for an officer who writes to the tables directly: a trigger and restrictive policies. A row starts as a claim. A claim changes hands only as the app allows (an error, a lapsed claim, the officer's own take-over); a lapsed or taken-over `sending` row only becomes `unknown`, or, written by its own run with the token, goes back to `queued`. A renewal, `sending` and a result need the run's token, which the write carries in `claim_proof` and the trigger checks against the hash and never stores. `unknown` becomes `error` only, with no Gmail id or send time. A `sent` row is final and cannot be deleted. Only a `queued` claim is deleted, by the officer whose run holds it or once it lapsed; a `sending` row is never deleted, so the address cannot be claimed afresh and mailed again. A campaign's subject and body never change, and its QR choice changes, or the row is deleted, only until a message of it went out. The owner, the import script (service role), a backup restore (security definer, as the owner) and foreign-key actions are not checked. No session setting turns the checks off: `sce.restoring` no longer does.
- **A send whose answer was lost.** A network error or a 200 without a message id may mean Gmail sent the message. It is never retried. The row becomes `unknown`, the run stops, and no run claims that address again. A dead run's message in flight (`sending` past its lease, or taken over) becomes `unknown` the same way; the log and the recipient list show a `sending` row as unknown as soon as its lease is over, before any claim writes it. The log shows "Không rõ đã gửi" and says to check the Sent folder; `comms.markNotSent` (behind a confirm) turns it into an error that can be sent again. A message turned unknown by a take-over is not confirmed unsent until the first run's lease is over, since that run may still record Gmail's answer; the refusal names the time to check again.
- **Ports and fakes.** Every external call goes through an interface with a fake. `GmailTransport` (`domain/transport.ts`) has `gmailTransport` and `fakeTransport`. `GoogleIdentity` (`components/google-identity.ts`) has `gisIdentity` and the test fake. `SheetSource` (`server/sheet-source.ts`) has the guarded Google fetch and `fakeSheetSource`. Under `SCE_DEV_MEMORY=1` the page uses the fake transport and never loads GIS, and the registered commands read the dev fixture sheet (`server/dev-sheets.ts`) without opening a connection. Tests build the commands with `createCommands({ sheets })` and never reach Google.
- **Sheet fetch (SSRF guard).** It fetches only a URL `toSheetCsvUrl` wrote (https, `docs.google.com`, the export or publish endpoint, `gid` kept). It follows redirects by hand, each to https `docs.google.com` or `<label>.googleusercontent.com` on port 443 with no credentials. IP literals, private and metadata addresses, http and look-alike hosts are refused before any request. The body is capped at 5 MB and the fetch at 10 s, and an HTML answer (a sheet that is not shared) is an error.
- **Form sync.** `comms.syncForm` stores responses keyed by a hash of who answered when (timestamp as typed, email, phone, name; the answers too when there is no timestamp), so it is idempotent, and a column added to the sheet or a corrected answer is not a new response. Columns are detected by scoring or set by staff (`comms.saveColumnMap`). The RSVP reader is conservative by construction (`domain/answers.ts`): no sentence is read for its meaning. After normalisation (NFC, lower case, old-style tone marks, single spaces, trailing particles such as "ạ", "nhé", "nha" and full stops removed; a question mark stays), an answer is applied only when it is exactly one of the Form's own choices that staff gave a meaning (`comms.saveAnswerLabels`, matched first) or one of the canonical answers in `CANONICAL_ANSWERS` ("Có", "Vâng", "Có tham dự", "Xin xác nhận tham dự"; "Không", "Không tham dự", "Không thể tham dự", "Xin phép vắng mặt", "Từ chối"; "Cử người đi thay", "Cử đại diện", "Ủy quyền"), typed with or without diacritics, with "ko", "k", "hok" or "khg" for "không" inside a listed answer. A plain-typed answer with "vang" (vâng or vắng) and a bare "k" (also "ok") are not canonical. Everything else (a clause added, "nhưng", "bận", "nếu", a question, a scope word such as "buổi chiều", "đc", "n/a", English, emoji, several lines) is `review`: matched to the guest, never applied, and listed on the Form screen under "Câu trả lời cần xem lại" with the answer as typed, the guest and three buttons, "Xác nhận tham dự", "Từ chối" (behind a confirm, since it frees the seat) and "Bỏ qua". A decision goes through `comms.resolveResponse` (`answer`) and `guests.applyRsvp` at the response's own time, and is audited. A substitution needs an exact substitute answer and a name in the substitute column; a name such as "Không", "-", "n/a", "Tự đi" or "Không rõ" names nobody, and a substitution without a name is review. The banquet cell is read the same way and an unclear one leaves the guest's banquet as it is. The Form screen lists each answer waiting for review once, with its count, to be saved as a Form choice; the next sync applies the waiting answers a saved choice now reads. Timestamps follow the sheet's own date order, from its rows: the reading that can read every date, then the one that puts none in the future, then the only one whose times go one way (forward, or back for a sheet sorted newest first) and whose newest answer is from the last week. When the rows cannot tell, no slash date is read, the responses wait for review, and the sync says so; a later sync that can tell gives every row not yet applied its time, so a `no_time` row becomes pending. A time after the server's clock is kept for review. A response matches by email, then phone, then name with organisation. Two candidates are parked for review. A definite answer goes through `guests.applyRsvp`, which applies only answers newer than the guest's last RSVP change. Auto-add (per event, default off) creates the guest through `guests.upsertMany` with no RSVP, then applies the answer through `guests.applyRsvp` at the response's own time. `comms.resolveResponse` matches, creates, decides, dismisses or reopens. The cron route runs `comms.syncForm` through the pipeline for every form with auto-sync on. The Form screen offers auto-sync only when `serverSyncReady()` (a system identity and `CRON_SECRET`); until change request 1 lands it is disabled and labelled "chưa hoạt động".
- **Mail merge and MIME.** One merge-field registry reads the real fields. Values are HTML-escaped where they land, and the template is sanitised before and after the merge (`sanitizeRichHtml` from `@/core/text`). The preview renders through the kit's `RichHtml`. The MIME builder refuses CR/LF in every header, writes RFC 2047 encoded-words, folds lines at 76/78 characters and caps the message at the 5 MiB JSON body.
- **Audit.** Every command is audited by the pipeline, and every write is a mutation: a run writes one row for its claim, one for its first mark (`comms.markSending`, "ĐANG GỬI THƯ") and one per message (`comms.recordDeliveries`, which also names the next message it marked). Ten recipients and a rate limit write 12 rows (23 before this pass); a run of 2,000 writes about 2,000 plus a renewal row every 5 minutes. A mark whose claim was lost writes its own row. `comms.renewClaims` writes one only when it renewed something. Comms writes no audit row itself and names no writer. A path that throws after a write stuck throws `CommandError(kind, message, undefined, entry)`, and the pipeline writes the entry under the command's `authorize.perm` (src/features/README.md, "Audit rows for partial failures"). Such paths: `startCampaign` (claims it could not free again, or a message in flight turned unknown, or a new message that could not be taken back out), `recordDeliveries`, `releaseDeliveries`, `markNotSent`, `renewClaims` (some leases renewed), `syncForm` (new rows stored, times read again or answers applied) and `resolveResponse` (create). Each writes exactly one row of its own, which tests assert. A row the database refuses leaves the failure as it was and the entry in the server log. A change that saved but whose row was refused returns ok with `unaudited`, and the page shows core's warning instead of the success text; tests run every send command, `syncForm` and `resolveResponse` under a refusing writer. Every action is a literal in the database's action set and every entity an ASCII identifier (`audit-strings.test.ts` scans each `audit()` call). A `guests.markInvited` refusal no longer fails a recorded send. The audit names the invitations to fix by hand.
- **Secrets.** The Gmail token sits only in a ref. It is sent only in the `Authorization` header, never stored (a test spies on `Storage.setItem`), and revoked on sign-out, on a sender change and when Google will not name its account. A popup answered after the sender changed is revoked, not kept. `CRON_SECRET` is compared as equal-length SHA-256 digests and never echoed. Nothing in comms calls `console`.
- **Tests** (`src/features/comms/__tests__/`, 817 in 18 files). They cover parsing (`answers.test.ts`: the 116 phrasings of the earlier reader relabelled, the reviewers' corpus in `rsvp-corpus.ts`, the canonical list as a snapshot, a generated corpus of more than 10,000 phrasings that must read as review unless exactly canonical, and the banquet answers, each typed with and without diacritics), merge, MIME, the dispatcher, the transport, the SSRF guard, the sheet sources, the cron auth, every command (permissions denied with RLS bypassed, other departments), claims, tokens, take-over, renewal and releases with the lease (Date pinned to the command clock, since memoryDb stamps rows from Date), partial-failure audits through a fault-injecting Db (`failingWrites`) and saves whose row is refused (`runWith` takes a stand-in writer), the token hook, rendering of hostile text and of every send-panel, log and review-list state, and the legacy importer. A sync of 108 answers a person must read changes no guest. `sql.test.ts` applies every migration on PGlite and checks the deliveries checks, policies and guard trigger on Postgres, one test per rule and per attack (a colleague taking, completing or deleting a live claim; a made-up sent row; a sent or imported row turned into an error or deleted; a `sending` row deleted, live or lapsed; `sending` back to `queued` without the token; unknown confirmed unsent with a Gmail id; a forged `sce.restoring`; a campaign template rewritten), plus a guest delete and a backup restore that still work. `e2e-dev.test.ts` (which mocks `server-only`, reached through `core/auth/admin`) runs the real registry, dev seeds and registered commands in the dev memory runtime with any network call failing the test. It invites, sends through the fake mailbox, reads the delivery log, syncs the dev sheet so `guests.applyRsvp` sets confirmed and declined and a sentence waits for review, and checks the audit. It also checks that a second run of the same message mails only the address that failed, that a rate limit is retried by itself, also when a renewal falls due during the retry, that ten recipients write 12 audit rows, that an expired token stops the run and resumes without re-sending, that a second tab of the same officer sends nothing the first holds, that a crash between Gmail's answer and the record does not re-send, not after the lease and not on a take-over, that a run 36 minutes long keeps its tail by renewing, that a lost answer is not re-sent until marked, and that mixed yes/no answers never decline a confirmed guest.

## Contract change requests

1. **Service identity for the cron route** (core, `src/core/auth`). `cronSystemContext` has no production actor, so `/api/cron/rsvp-sync` answers 503 outside dev memory (m4a B22, m4c B31). Ask: a `systemRequestContext()` for route handlers, with an actor holding `comms.rsvp.manage` and `guests.write` on every event, audited as "Hệ thống (đồng bộ tự động)". The same caller would serve core's scheduled backups (core status Q8).
2. **Kit file input** (components). User attachments in invitations (legacy "File đính kèm", m4a B30) need a file picker. This is the same request as guests change request 3 and directory change request 1. The MIME builder already takes attachments, encodes each once and caps the total.
3. **Audit on a thrown `CommandError`** (core, `src/core/commands`). **Resolved** by core on dev (65106c1): `CommandError` takes an `AuditEntry` as its fourth argument and the pipeline writes it. `auditPartial` is gone; its six sites throw the entry (see Audit above).
4. **`contract.ts` is behind the tables** (frozen). `RsvpResponse.match` lacks `'manual'`, and the contract has no `applyStatus` (now with `'review'`), `rsvpAnswer` or the form's `answerLabels`. `EmailDelivery` lacks `recipientName`, `providerMessageId`, `imported`, `claimToken` (now a hash) and the write-only `claimProof`, and `DeliveryStatus` lacks `'sending'` and `'unknown'`. The campaign message (`sce_tcsk_email_campaigns`) has no contract type. `resolveGoogleClientId` in the contract still throws `not implemented`; the index exports the real one from `domain/client-id.ts`. Ask: align the contract types with `server/tables.ts` and re-export the function.
5. **memoryDb parity for table checks, restrictive policies and triggers** (core, `src/core/db/memory.ts`). memoryDb emulates the permissive RLS policies, NOT NULL and unique keys, but not CHECK constraints (`sent_has_evidence`, `queued_has_token`, `unknown_has_text`, `status_check`), restrictive policies (`imported` only by the import script, a row starts as a claim, only unsent claims deleted, a campaign fixed after its first send) or the delivery and campaign guard triggers. memoryDb keeps `claim_proof`, which Postgres never stores; nothing reads it. The comms commands never write such rows, and `sql.test.ts` checks them on PGlite, but a feature bug that did would pass in tests and dev memory and fail only on Postgres. Ask: emulate CHECK constraints and restrictive policies from the SQL catalog, or document that they are Postgres-only.

## Not verified against real services

- Gmail `users/me/messages/send`: the request shape, the error reasons mapped to auth/quota/rate (`dailyLimitExceeded`, `userRateLimitExceeded`, `insufficientPermissions`), Retry-After handling, and the 5 MiB JSON body limit (inferred from Google's API limits, not measured).
- Gmail's handling of a From that is a send-as alias of the signed-in account (refused here).
- Google Identity Services: the popup flow, `error_callback` types, `expires_in`, `revoke`, and the `userinfo` response with the `openid email` scopes.
- Google Sheets: the `export?format=csv&gid=` and `pub?output=csv` redirects to `*.googleusercontent.com`, the status and content type of an unshared sheet, and Vietnamese CSV encoding.
- The `unique (campaign_id, email)` and version races between two claims or a claim and a renewal, on Postgres rather than memoryDb (`sql.test.ts` checks the constraints and policies on PGlite, not concurrent transactions).
- The deliveries lease uses the row's `updated_at` against the app server's clock, with a 2-minute skew margin; a larger skew is not guarded. memoryDb stamps wall-clock time. Postgres stamps transaction time, and the guard trigger compares it with the database's own `now()`.
- The guard trigger tells an officer from the import script and from foreign-key actions by `current_user` (`authenticated` or `anon` are checked). PGlite runs the officer as `authenticated` and a guest delete's `on delete set null` as the owner, as Postgres does; on Supabase this relies on PostgREST setting the `authenticated` role for a signed-in user and `service_role` for the import script. Not checked against a real Supabase project.
- A message marked `sending` whose mark's answer was lost (the run stops unsent) shows "Đang gửi" until its lease runs out, then "Không rõ đã gửi", though it never went; the officer's check of the Sent folder settles it. A record marks the next message 1.2 s (the spacing) before it is sent, so a tab that dies in that gap leaves the same state.
- Whether Gmail can accept a message and still answer with a network error or a 200 without an id often enough to matter (treated as unknown either way).
